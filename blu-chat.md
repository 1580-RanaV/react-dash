# Blu Chat — Feature & Scenario Reference

This document catalogs every scenario, component, and interaction currently mocked in Blu Chat, with what it does and where it lives. Implementation: `src/components/BluChat/` — `index.tsx` is the shell (header, thread switcher, composer, message list); everything trigger-word-driven or reusable lives in `src/components/BluChat/blocks/`; shared types/constants/helpers are in `types.ts`, `constants.tsx`, `utils.tsx`. Concurrent thread state lives one level up in `src/components/BluMessagesContext.tsx`. The chart/table artifact behind `custom-report` is `src/components/CustomReportResult.tsx` (shared with the Home-dashboard widget feature, so it stays outside the `BluChat/` folder).

Most scenarios are triggered by typing an exact **magic word** into the composer and pressing Enter — this is a mock data-generation shortcut, not a real AI backend. Every trigger word is checked in `sendMessage()` inside `index.tsx`.

---

## 1. Window modes

Blu Chat renders as the same component in three shells, switched by the `mode` prop (`BluMode`: `"panel" | "float" | "fullscreen"`).

- **Panel** — the default: a docked sidebar/rail chat opened from the "Ask Blu" rail button, rendered inline in `DashboardShell`.
- **Float** — a small draggable floating window (header is a drag handle via `onHeaderMouseDown`), toggled from panel mode's window-control button. Shows a mascot avatar chip in the header instead of the thread switcher.
- **Fullscreen** — a dedicated route (`/blu`, `BluFullscreenView.tsx`). The composer becomes `position: absolute`, docked to the bottom and self-centering via a `translateY(-100%)` CSS trick (no JS-measured repositioning needed); on first load with no messages it shows a centered "landing" heading + composer that smoothly glides down to the docked position once the user starts typing or sends a message.
- **Minimize / back-to-panel** — float and fullscreen both have a control to snap back to the panel shell; panel has controls to pop out to float or fullscreen. These are plain window-chrome buttons in the header (`AppWindow`/`Maximize2`/`Minimize2` icons), separate from the thread switcher.

All three modes share one `messages` state per active thread (via `BluMessagesContext`), so switching modes never loses conversation state — it's the same thread continuing in a different shell.

## 2. Thread switcher (top-left header component)

Panel and fullscreen modes show a pill button in the header: icon + current thread title (truncated) + chevron. Clicking it opens a dropdown panel (`w-88`).

- **Search chats** — a text input at the top of the dropdown filters the thread list live by title (case-insensitive substring match).
- **New chat button** — creates a fresh empty thread and switches to it immediately (`createThread()` in `BluMessagesContext`).
- **Thread list rows** — each shows the thread's title and a relative time ("2d", "1w"), or "Current" for the active one. Pinned threads sort to the top of the list and always show a small filled pin icon next to the title, even when not hovering.
- **Hover actions (Pin / Rename / Archive / Delete)** — hovering a row crossfades its trailing time label into four icon buttons (`h-7 w-7`, ghost style) without any layout shift (the trailing slot is a fixed-width absolutely-positioned crossfade, not a `hidden`/`flex` swap, specifically to avoid the title column reflowing on hover):
  - **Pin** toggles `thread.pinned`, re-sorting it to the top.
  - **Rename** swaps the row's title into an inline text input (autofocus, save on Enter/blur, cancel on Escape).
  - **Archive** marks the thread `archived` (and un-pins it), removing it from the main list; if it was the active thread, switches away to the next available one.
  - **Delete** removes the thread outright, with the same active-thread fallback behavior.
  - All of these (and Restore/Delete in the archived view) share one neutral ghost-hover background (`hover:bg-stone-100 dark:hover:bg-white/6`), matching the New chat row, the Archived-chats toggle, and the thread rows themselves — Delete's red hover is the one deliberate exception, since it's destructive.
- **Archived chats section** — a fixed row ("Archived chats" + chevron) sits below the scrollable thread list (not inside it, so it never scrolls out of view), toggling the whole dropdown's content into an archived-only view: same search filtering, a "Restore" (un-archive) and "Delete" action per row instead of the four normal ones. Seeded with 3 sample archived threads out of the box.
- **Notification icon** (inside the pill, replacing the static icon) — see §6.

## 3. Notification flow ("other threads have activity")

Trigger word: **`notification`**. Sends no Blu reply — it only flips UI state, simulating "something finished in a background thread."

- Marks 2 random **other** threads (never the currently active one) as unread (`unreadThreadIds`, a `Set<string>`).
- The thread-switcher header icon crossfades (blur+opacity, no layout shift) between three states: a plain outline icon (idle), a filled blue dot icon, and a ringing bell — the dot and bell **alternate every 2 seconds** for as long as any thread is unread, complete with a real rotation "ring" keyframe on the bell. Once every unread thread has been opened (dots cleared), it reverts to the idle icon and the alternation stops — "once it's gone, it's gone."
- Each unread thread shows a small blue dot next to its title in the thread-switcher list; opening that thread clears its dot (`markThreadRead`).
- A dismissible strip appears directly above the composer (rounded top corners only, no gap, sharing one continuous border with the composer box below it, off-shade `var(--muted)` background): **"New activity in other chats."** Clicking the text opens the thread switcher; an X dismisses it. It reappears on a fresh `notification` trigger even if previously dismissed, and re-renders in fullscreen mode docked correctly above the composer using the tracked `composerHeight`.

Trigger word: **`upgrade`**. Also sends no Blu reply — the "upgrade" text still appears as a normal sent user message, but instead of a reply it opens a blue-tinted strip in that same above-the-composer slot, with an **"Upgrade now"** button (navigates to `/settings/billing` via `useNavigate`) and a dismiss X. The copy itself has **two versions keyed off `mode`**, since panel/float has much less horizontal room than fullscreen: panel/float shows a short line, *"Upgrade to keep using Blu."*, that fits without truncating next to the button, while fullscreen shows a two-sentence version, *"You're on a limited plan. Upgrade to keep using Blu."* Both are deliberately em-dash-free and plain-worded — earlier drafts used "interruption"/"uninterrupted," which read as needlessly long and formal for a one-line strip. Unlike the attachment/queue notice (borderless, see below), this one keeps a soft blue-tinted border (`rgba(0,128,255,0.25)` on the top/left/right) — with a real border, `items-center`, and fixed-height (`h-6`) button/X so the text, "Upgrade now" pill, and dismiss X all sit on one clean baseline rather than top-aligned against each other's differing heights. All three of these above-composer strips — attachment notice, upgrade prompt, and the unread-thread notification — share one `topStripVisible` flag that decides the composer's top border/corner-radius, so only one shows at a time; the attachment notice takes priority over the upgrade prompt, which in turn takes priority over the notification strip.

All strips — attachment/queue notice, upgrade prompt, and the notification strip — now share the exact same **`2px solid var(--border)`** outline on top/left/right that the composer box itself uses, so the border reads as one continuous line running from the strip straight into the composer below it, regardless of which strip's tint (red, blue, or neutral `var(--muted)`) is showing. The attachment/queue notice's text is never `truncate`d: the row is `items-start` with a wrapping (not `truncate`d) span, so a message too long for the panel's width simply wraps to a second line and the strip grows taller, rather than clipping with an ellipsis.

## 4. Composer (the prompt box)

- **Text input** — a `contentEditable` div (not a plain `<textarea>`) so it can host inline rich chips. Rotating placeholder text cycles every 3s with a fade. The composer box itself is `px-4 pt-4 pb-4` with `mt-4` above the icon row and `gap-2.5` between the footer's pills (bumped up from `pb-3`/`mt-3`/`gap-2`) so the row of icons doesn't read as packed.
- **`@` mentions** — typing `@` opens the **entities/objects picker**: a category list (Journeys, Experiences, Avatars, Scenes, Poses, Design System, Catalog Feed, Events); picking a category then an item inserts a small inline icon+label chip directly into the text, matching the extracted text as `@Label` when sent.
- **`/` recipes** — typing `/` opens a filtered list of quick-start content recipes (Email campaign, SMS, Push, Social post, Banner, Subject lines, Product shot, Landing page, Nurture flow, Welcome series); the current route contextually promotes a relevant subset to the top. Picking one inserts a pill-style chip; recipes are excluded from the literal sent text (they render as their own chip row on the message instead).
- **`+` attach button** — a small dropup menu with three paths (References, Attach Files, Chat Settings). Only the item list itself floats next to the `+` button; picking **References** or **Chat Settings** closes that little menu and instead opens a **full composer-width strip directly above the prompt box** — the exact same slot and `2px solid var(--border)` top/left/right border treatment the `composerNotice`/`upgrade`/notification strips use, merging seamlessly into the composer's own top edge (no floating card stacking on top of anything). Each such strip has its own capitalized heading ("References" / "Chat Settings") in its header row (no divider line under it) and a close (X) button with a circular ghost hover.
  - **References** — browse by category (Assets, Attributes, Users, Events, Avatars, Scenes, Poses, Design System, Catalog, Feeds, Journeys, Experiences, Out of the Box, Boards) with a searchable item list; picking a category drills into the same strip (with a "Back to References" control), and picking an item inserts an inline reference chip directly into the prompt text (same mechanism as `@` mentions — this used to add a separate preview row above the composer, but that was moved inline so references read as part of the message itself).
  - **Chat Settings** — opens the same kind of strip showing three chip-row groups: **Response Depth** (Concise/Standard/Extended), **Model Tier** (Default/Premium/Max), and **Knowledge Scope** (Thread/Project — the same state as the composer's own "Project" pill toggle, so they stay in sync). Chips have **no border in either state**: unselected is plain muted text, selected fills solid blue (`#0080FF`) with white text — no outline style.
  - **Attach Files** / **Image settings** — the native file picker accepts any file; every upload (image, PDF, HTML, or Markdown alike) shows the same **square thumbnail treatment** in a preview grid above the composer (`h-24 w-24`, bumped up from an earlier, smaller size), with a brief uploading-blur transition. Images get a real photo thumbnail. Non-image kinds (PDF/HTML/MD/generic) get a plain `var(--muted)` tile — **no file-type icon** — with two overlaid labels instead: the **file name**, anchored to the tile's top-left corner, wrapping across up to **3 lines** before it truncates with an ellipsis (`line-clamp-3`, spanning the tile's width rather than being cut off after just a few characters on one line), and a small **type badge** ("PDF"/"HTML"/"MD"/"FILE") in the bottom-right corner. The badge is intentionally **neutral** — a semi-transparent gray chip with theme-aware text color, not a per-type color — so it reads correctly in both light and dark mode without a whole extra color system to maintain. This same tile treatment carries through to how the file renders once the message is actually sent, in the conversation history (there at `h-28 w-28`, one size step up again, since history tiles have more breathing room than the composer's preview row). Image settings (aspect ratio, background, style) is a separate, unrelated tag that surfaces in the same References strip, since it's a generation setting rather than an attached file.
  - **Preview grid layout** — in panel/float mode the preview grid is a fixed 3-column grid (`grid-cols-3`), so attachments wrap into rows of 3 (two full rows for the first six, a third partial row for the seventh); in fullscreen mode it's a single non-wrapping row (`flex flex-nowrap`, scrolling horizontally if it were ever to overflow) since the wider composer comfortably fits all of them side by side.
  - **7-attachment cap** — `MAX_ATTACHMENTS` in `index.tsx`. Selecting files beyond the 7th silently declines to attach the extras (only the first N that fit are accepted) and surfaces a dismissible strip — "Max 7 files attached. Remove one to add another."
  - **5MB per-file size cap** — `MAX_ATTACHMENT_SIZE_BYTES` in `index.tsx`. Any single file over 5MB is rejected the same way, surfacing "File size exceeds limit" in the identical strip. Both checks run in the same `onChange` handler (size filtered first, then the count cap applied to what's left), sharing one `attachNotice: string | null` state that holds whichever message applies — so only one ever shows at a time, and picking a fresh batch of files always re-evaluates and can re-trigger it even if previously dismissed.
  - Both notices use the same rounded-top-corners-merging-into-the-composer shape as the notification strip, but a **red tint** (soft red background + red text) so they clearly read as a limit/warning rather than an FYI. Unlike the notification strip (which keeps the neutral `var(--border)` outline), this strip has **no border at all** — the red fill runs flush to the edges, reading as one solid blended shape rather than an outlined box sitting on top of a red background. Its dismiss X is a circular ghost button (`rounded-full`), matching the circular-icon-button convention used elsewhere rather than the squarer `rounded-md` the notification strip's own X still uses. See §3 for how this fits into the shared `topStripVisible` priority with the `upgrade` and `notification` strips.
- **Queue intercept** — typing anything matching `/^q\d+$/` (`q1`, `q2`, `q3`, ...) stashes the text into a small queue list shown above the composer instead of sending it immediately, capped at `MAX_QUEUE = 4` — a mock "batch up requests" affordance. Each row renders as a full-width rounded `var(--muted)` chip (`rounded-lg`, `px-2.5 py-2`), matching the same row proportions as the thread-switcher's list rows rather than a bare divider-separated line list. Each row supports **click to expand** (an accordion reveal below the row, wrapped text capped at 4 lines via `line-clamp-4` with an ellipsis if it's still longer — just enough to jog memory of what was typed, not a full editor), **double-click to edit** (autofocus, save on Enter/blur, cancel on Escape), **delete** (hover-revealed), and **drag-to-reorder** via a grip handle, built on the same `@dnd-kit` `DndContext`/`SortableContext`/`arrayMove` pattern already used for sortable rows elsewhere in the app (`TasksView.tsx`'s sort-rule list). Trying to queue a 5th message doesn't queue it and doesn't send it as a literal message either — it surfaces the same borderless red composer-notice strip used for attachment errors: "Queue full. Delete one or wait for a slot to open up."
- **Toggles** — three pill buttons sit in the composer footer:
  - **Project / Thread** — a two-state context-scope toggle (was previously a three-way Project/Org/Thread dropdown; simplified to a plain click-to-flip pill with a Brain icon).
  - **Plan** — arms "plan mode" (currently just a visual toggle state alongside the `plan` trigger word's own flow, see §5).
  - **Web** — a visual-only toggle for "search the web."
- **Send / Stop button** — a circular button that shows an up-arrow normally; while a `custom-report`-family message is generating, it swaps to a square "stop" glyph (`activeReportId` tracks the in-flight report). Clicking it while generating replaces that message in place with "Report generation was stopped. Try generating again." instead of deleting it — the card doesn't just vanish.
- **Voice input mic** — sits inline inside the text-input area itself, top-right corner (`position: absolute`, `top-0 right-0`), aligned to the same baseline as the placeholder/first line of typed text rather than floating above the send button. It's the same `h-7 w-7 rounded-full` footprint as the send button below it (with the standard ghost `hover:bg-stone-100 dark:hover:bg-white/8` treatment used elsewhere), so the two sit in the exact same column — confirmed by measuring both buttons' center X in a live check. Visible only while the editor is empty, fading out (`opacity`/`pointerEvents`) the moment the user starts typing; the input and placeholder both reserve `pr-7` so text never runs under it. Purely visual in this mock; no real speech capture is wired up.
- **Sent file attachments** — persist on the message as the same square tiles described above. Image tiles stay clickable and **previewable**, opening a fullscreen lightbox overlay (dark blurred backdrop, close button) with the full-size image; PDF/HTML/MD/generic tiles are static (their badge is enough context — there's no real file content behind the mock to open).

## 5. Trigger-word message types (the `blocks/` components)

Typing one of these exact words and pressing Enter drives `sendMessage()` down a specific branch that attaches a flag to the resulting `ChatMessage`, which the render switch in `index.tsx` maps to one of these components.

| Trigger word(s) | Component | What it shows |
|---|---|---|
| `run`, `run-2`, `run-3` | `CreationRunStatus` (`blocks/CreationRun.tsx`) | One or more **independent, simple task cards** stacked vertically (Create Avatar / Create Pose / Create Scene depending on the number). Each card is just a progress-ring badge + title — no subtitle, no status chip, no expand. The ring spins (indeterminate) for 2s per task, then fills solid blue with an animated checkmark. This is the "single card" concept — no stage narrative. |
| `run-declined` | `CreationRunStatus` with `declined` | Same single task card and timing as `run`, but once the 2s indeterminate spin finishes, the badge fills with a small solid red circle and a white X (`DeclinedBadge`, shared with `accept-run`) instead of the blue checkmark. |
| `live-run` | `LiveRun` (`blocks/LiveRun.tsx`) | **One card that represents several sequential stages.** The title itself cycles through real stage names (from `QueryStages.tsx`'s `STAGE_ROWS`) with a shimmer-text effect while a stage is "active," and the same shared progress-ring badge fills incrementally as stages complete. The chevron isn't gated on full completion — as soon as the *first* stage finishes and the next one starts shimmering, the chevron already appears and can be expanded, revealing the completed stage(s) so far (name + duration) deposited in the list exactly like the finished state, growing one row at a time as each subsequent stage completes. Only once every stage finishes does the card also show a "Total time" row and a "What was asked for" summary appended below the (now-complete) stage list — the "stages inside one run card" concept, as opposed to `run`'s flat list of separate cards. |
| `live-run-declined` | `LiveRun` with `declined` | Identical stage-by-stage playthrough as `live-run` (same shimmering titles, same progressively-revealed completed-stage list), but once every stage finishes, the badge shows the shared red `DeclinedBadge` (filled red circle + white X) instead of the blue checkmark. |
| `accept-run` | `AcceptRun` (`blocks/AcceptRun.tsx`) | **A decision card using the exact same shell as `run`/`live-run`** — same `max-w-64` width, `rounded-xl`, `var(--content-bg)` background, `1px solid var(--border)`, shadow, and `fade-up` entrance animation. Just three things inside it: a bold heading ("Want me to place this restock order?"), a plain wrapping two-sentence description (no chips, no colored pills — just muted body text: "Reorder waffle cones from Cone King with lead time 7 days. Stock is projected to run out by Friday at current sales pace."), and an Accept/Decline button pair — no progress ring, no confidence indicator, no "Alternatives" button. Deciding collapses the card to a single row matching the rest of the run-card family: the badge slot fills with the shared solid-blue-fill-plus-checkmark badge (`LiveRunProgressCircle`, same component `run`/`live-run` use) on Accept, or a small filled red badge with an X on Decline, sitting beside the full heading (wraps rather than truncates, so the whole question stays readable). |
| `custom-report` | `CustomReportBlock` (`blocks/CustomReport.tsx`) → renders `LiveRun` while "running," then `CustomReportResult` once settled | A full analytics narrative: summary paragraph, a result-confidence badge (Confident/Qualified/Declined) with an "Assumptions" popover, a KPI-tile + line-chart card, and an action row (Show in table, Export, Save, Embed, Add to dashboard). Each action opens its own modal. |
| `custom-report-declined` | same, but renders `DeclinedResult` instead of the chart | Models Blu declining to answer (e.g. a dimension the workspace doesn't track), with a "Declined" badge, a plain-language reason, and a "Suggested next step" follow-up prompt instead of a chart. |
| `custom-report-no-embed` | same as `custom-report`, `noEmbed` prop | Identical output, but the Embed button is hidden and a yellow "Embed not available" badge (same visual tone as "Qualified") sits next to the confidence badge, with a hover tooltip explaining why. |
| `add-event` | same as `custom-report`, `extraEvent` prop | Adds a third tracked event (Signup) to the narrative, KPI tiles, and chart legend/lines, alongside page views and cart events. |
| `create-recipe` | (no visual block itself) fires a `blu-recipe-run` window event | Opens the separate Recipe Canvas feature; when that canvas runs a recipe, its steps come back through the same event bus and render as... |
| *(via recipe-canvas run)* | `ExecChecklist` (`blocks/ExecChecklist.tsx`) | A step-by-step checklist that advances one step every ~1s (checkmark → spinner → next), with a "N/M done" counter — a generic "recipe is executing" progress card. |
| `plan` | `PlanCard` (`blocks/PlanCard.tsx`) | See §5a below — a distinct, multi-part flow rather than a single message block. |
| `feedback` | `FeedbackQuestionnaire` (`blocks/FeedbackQuestionnaire.tsx`) | See §5b below. |
| `failed` / `error` | inline error block (in `index.tsx`, not its own file) | A red-tinted card with an error icon, a plain-language message, and a "Report bug" button (`mailto:` link). |
| `create a journey` / `create journey` (regex match, not exact word) | inline journey chip + `JourneyPreviewOverlay` (`blocks/JourneyPreviewOverlay.tsx`) | Blu's reply streams in normally, then attaches a small purple "journey chip" pill; clicking it opens a fullscreen modal with a hand-drawn SVG journey canvas (trigger → email → wait → branch → two ends) and an "Open in Editor" CTA. |
| *(any other text)* | `StreamingReply` (`blocks/StreamingReply.tsx`) | The generic fallback: Blu's canned reply token-streams in word-by-word with a blinking cursor, then (for both this and the journey case) shows 2–3 canned follow-up suggestion buttons. |

### 5a. Plan mode (`plan`)
Sending `plan` gets a short Blu acknowledgement plus a `PlanCard`: a summary line, an expandable numbered-steps preview, and Skip/Details/Approve actions. "Open full review" opens a fullscreen reading view of the entire plan text with its own Approve/Skip. Approving or skipping posts a corresponding Blu confirmation message and dismisses the card. In fullscreen chat mode, the card is docked directly above the composer (using the same measured `composerHeight` the notification strip uses) so it can never overlap or visually collide with the input box, and it shares the same fixed `max-w-64` width as the `run`/`live-run` cards for visual consistency.

### 5b. Feedback stepper (`feedback`)
`FeedbackQuestionnaire` is a 3-question radio-button wizard (feedback type → area → urgency), each with a free-text "type something" fallback option. A progress dots strip at the bottom (filled = done, ringed = current, hollow = upcoming) tracks position; Next/Submit is disabled until an answer is picked. On submit, it silently sends a formatted "Feedback:\n• ..." message back into the conversation as if the user had typed it, then shows a "Feedback sent" checkmark confirmation card in its own place.

### 5c. Thinking / loading state
While Blu is "typing" (before any specific block resolves), `LoadingState` (`blocks/LoadingState.tsx`) shows a tiny animated pixel grid plus a shimmering label and a live elapsed-time counter (mono, tabular digits). It supports five wavefront patterns (Drive, Dots, Orbit, Ripple, Beam); the one actually wired up for the generic "Thinking" state draws a capital **"I"** stroke-by-stroke each cycle (the "Beam" variant) — top flange, then the middle stem, then the bottom flange, looping.

## 6. Message-level actions (hover toolbar under every message)

A row of icon buttons fades in on hover (or stays visible by default under the single most-recent completed Blu message):

- **Copy** — copies the message's raw text to the clipboard; swaps to a checkmark for 1.5s as confirmation.
- **Fork from here** — (user and Blu messages both) duplicates the conversation up to and including that message into a brand-new thread titled "`<original title> (fork)`", and switches to it immediately — a git-branch icon, tooltip "Fork from here." All messages up to the fork point stay fully visible in the new thread (not just implied context) — `BluThread.forkedFrom` records the source thread's title, and the forked thread shows a small non-dismissible pill: *"Forked from "&lt;source title&gt;""*. It renders at the **bottom** of the message list, right after the last message and directly above the composer — not at the top — so it's the thing the user actually sees as they're about to type their next prompt, rather than something they'd have to scroll up to notice.
- **Edit** (user messages only) — turns the message into an inline auto-growing textarea with Cancel/Send; sending re-submits the edited text as a fresh message and discards everything that came after the original (since a stale Blu reply no longer matches the edit).
- **Good / bad response** (Blu messages only) — a combined thumbs-up/thumbs-down icon opens a small reaction menu; picking one records it and swaps the toolbar icon to a filled thumbs-up or thumbs-down. Picking **Bad response** additionally opens a "What went wrong?" feedback modal: three optional toggle chips (Inaccurate / Tone / Length, multi-selectable), a free-text detail field capped at 250 characters (with a live `n/250` counter), and Cancel/Submit — the same modal chrome (rounded card, circular close button) used by the Save/Embed modals elsewhere in Blu Chat.
- **Regenerate** (Blu messages only) — clears any existing reaction and re-streams that same reply from scratch (`isStreaming: true` again).
- **Follow-ups** — 2–3 canned suggested next prompts render **only under the single most-recent Blu message in the thread** (not under every past reply that happens to carry follow-up data) — clicking one sends it as if typed. This was a deliberate fix: earlier, every Blu message that had ever carried follow-ups rendered its own stale copy of them.

The whole action row (and Copy specifically) is suppressed for message types that have no meaningful "text" of their own — `run`, `live-run`, feedback forms, typing/streaming placeholders, errors, and the plan card.

## 7. Timestamp dividers

A small centered timestamp doesn't render above every message — that would be noisy. Instead, each **user** message carries its own `timestamp` (set once, at send time), and the message list keeps a running "last shown" timestamp as it renders top to bottom: a divider only appears above a user message when either it's the very first message in the thread, or at least **30 minutes** have elapsed since the last divider that was actually shown (`TIMESTAMP_DIVIDER_GAP_MS` in `index.tsx`). Sending several messages back-to-back — the normal case — shows exactly one divider for the whole burst; the 30-minute gap is really just a trigger for "has enough time passed to be worth a fresh label," not a rule about the label's content itself. Blu's own replies never carry their own divider — they're considered part of the same "moment" as the prompt that triggered them.

The label's wording (`fmtTimestampDivider` in `index.tsx`) depends on how far the message's calendar day is from today, checked in this order:
1. **Same day** → `Today 2:06 PM`
2. **One day back** → `Yesterday 2:06 PM`
3. **2–6 days back** → the weekday name → `Monday 2:06 PM`
4. **7+ days back** → a full date → `August 24 2:06 PM`

## 8. Message bubble styling

- **User messages** get a background bubble (`var(--muted)`, an off-shade fill distinct from the page background in both themes) with a deliberately sharp (4px, vs. 16px elsewhere) top-left corner — a subtle "speech bubble pulling toward the avatar above it" cue, iMessage-style. Long unbroken strings (no spaces) wrap inside the bubble via `break-word` rather than overflowing the panel — this required making the message's `min-w-0` wrapper always `w-full` so it actually inherits the row's constrained width instead of shrink-wrapping to its own content inside a non-stretching flex column.
- **Blu replies** intentionally have no background at all — kept as plain text so the two roles are easy to tell apart at a glance without needing the avatar.
- Both roles keep their avatar (Blu's mascot icon; the user's own `dp.png`) and name label above the message.

## 9. Underlying architecture notes (for future edits)

- **Concurrent threads**: `BluMessagesContext` holds a `BluThread[]` (id, title, messages, sessionTime, relative time label, `pinned?`, `archived?`) so switching threads — or switching window mode entirely — never loses another thread's in-progress state, the same way browser tabs behave independently.
- **Trigger-word plumbing**: adding a new magic word touches four spots in `sendMessage()` inside `index.tsx`: the `const isXxx = ...` check, the initial message-push branch, the reply-timeout branch (or its exclusion from the generic fallback), and the render-switch that maps the flag to a component.
- **Shared building blocks worth knowing about before adding new ones**: `LiveRunProgressCircle` (the ring-badge with an `indeterminate` spin mode) and `DeclinedBadge` (the small filled-red-circle-plus-X badge) both live in `blocks/LiveRun.tsx` and are shared across the whole run-card family — `run`/`run-declined` (`CreationRunStatus`), `live-run`/`live-run-declined` (`LiveRun`), and `accept-run` (`AcceptRun`) all import them rather than each keeping their own copy. `QueryStages.tsx` is kept only as the source of the stage-name/timing constants (`STAGE_ROWS`, `STAGE_MS`, `TOTAL_MS`, `ASKED_FOR`, `fmtDuration`) consumed by `LiveRun` — its own standalone UI is commented out, not deleted, in case it's needed again.
